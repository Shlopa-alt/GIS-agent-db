# База данных проекта

Агентная база под узлы 3–4 технологической схемы: сбор сырых данных и их
паспортизация. Развёрнута локально, отдельным экземпляром СУБД на диске F:
(права администратора не требовались, системный PostgreSQL на 5432 не тронут).

## Установка

| Параметр | Значение |
|---|---|
| Версия | PostgreSQL 18.3 + PostGIS 3.6.2 (GEOS 3.14, PROJ 8.2.1, GDAL 3.9.2) |
| Каталог хранилища | `C:\Users\Grisha\GIS-DB` на рабочей машине; ищется сам — переменная `GIS_DB_ROOT`, затем `~\GIS-DB`, затем `F:\GIS-DB`, затем рядом с репозиторием; опознаётся по каталогу `secrets` |
| Каталог программ | `<хранилище>\pg18` |
| Каталог кластера | `<хранилище>\cluster` |
| Порт | **5433** |
| База | `gis_au_u`, кодировка UTF8, сортировка ICU `ru-RU` |
| Пуск / останов | `<хранилище>\start_db.bat`, `<хранилище>\stop_db.bat` (автозапуск при входе в систему) |
| Растры вне базы | `<хранилище>\raster` |
| Приёмный каталог | `<хранилище>\incoming` |
| Резервные копии | `<хранилище>\backup` |
| Пароли | `<хранилище>\secrets\*.pw`, доступ только текущему пользователю |

### Установка с нуля

```
python db/install.py --проверить      что будет сделано, ничего не менять
python db/install.py --суперпользователь postgres
```

Одна команда вместо четырёх шагов: проверка сервера (версия и наличие PostGIS
— до того, как что-то менять), роли с паролями в хранилище, база в UTF-8 с
сортировкой ICU `ru-RU`, расширения, накат миграций по учёту и сверка итога.
Повторный запуск безвреден: заведённые роли и существующая база не трогаются.

Запускается от суперпользователя кластера (на свежем сервере это `postgres`);
его пароль берётся из `GIS_DB_SUPER_PASSWORD` или `PGPASSWORD`.

**`gisadmin` суперпользователем не делается.** Раньше это выходило само собой:
расширения ставит только суперпользователь, а ставит их первая миграция. Теперь
расширения ставятся отдельным шагом от имени суперпользователя кластера, и
`gisadmin` остаётся владельцем схемы с правом заводить роли и базы. Своей
системе координат нужна запись в `spatial_ref_sys` — это право выдаётся явно,
а не целым суперпользователем ради одной таблицы.

Что делается после установки:

```
python db/set_password.py gis_human            пароль роли панели
python db/add_reviewer.py --кто ivanov         учётная запись человека
python scripts/db_load_datasets.py             наполнение данными проекта
python scripts/db_load_dictionary.py           снимок словаря признаков
```

Установка проверяется на каждый коммит: работа «установка с нуля» в
`.github/workflows/checks.yml` поднимает пустой сервер и проходит весь путь,
включая повторный запуск. Отдельная проверка следит, чтобы роль, которой схема
выдаёт права, кто-нибудь создавал — установщик или миграция, но не оба.

Сервер запускается от пользователя, а не службой Windows, и при выходе из
сеанса падает: в журнале кластера это `0xC000026B` или `0xC0000142` — рабочие
процессы не переживают завершение сеанса. Лечится повторным `start_db.bat`;
данные при этом целы (сервер восстанавливается из журнала предзаписи), но
после аварийного останова подъём занимает до минуты: сначала идёт сверка
каталога с диском, и всё это время попытки подключиться отвечают «the
database system is starting up». Если база должна
работать без вошедшего пользователя, её надо зарегистрировать службой
(`pg_ctl register`, права администратора).

## Роли

| Роль | Права |
|---|---|
| `gisadmin` | суперпользователь, миграции схемы, подтверждение паспортов |
| `gis_agent` | чтение, вставка, изменение — **без удаления**; в `staging` полноправен |
| `gis_human` | как `gis_agent`, но вправе ставить статус «подтверждён» — под ней работает панель |
| `gis_read` | только чтение (анализ, QGIS) |

Разграничение — техническое выражение правила «система автоматическая, кроме
удаления, лицензии и геологического смысла».

## Схемы

| Схема | Назначение |
|---|---|
| `data` | территории, слои-источники, сетка, ячейки, признаки, значения |
| `meta` | паспорта слоёв и признаков, лицензии, происхождение, реестр пробелов |
| `runs` | журнал прогонов: версия кода, манифест входов, метрики, артефакты |
| `kb` | справочник понятий: рудоконтролирующие факторы и условия наблюдения |
| `bridge` | связи данных и знаний; правки требуют подтверждения человеком |
| `staging` | приёмный буфер агента, черновая площадка |

## Миграции

Запускать по порядку от `gisadmin`:

| Файл | Что делает |
|---|---|
| `sql/001_bootstrap.sql` | расширения и схемы |
| `sql/002_schema.sql` | таблицы данных, паспортов, происхождения, прогонов |
| `sql/003_confirmation_rules.sql` | права ролей и триггеры подтверждения |
| `sql/004_srid.sql` | своя система координат SRID 990018 (сетки ГИС Интегро) |
| `sql/005_gaps.sql` | реестр пробелов: чего в проекте физически нет |
| `sql/006_llm_calls.sql` | журнал обращений к языковой модели (`runs.llm_call`) |
| `sql/007_review.sql` | панель подтверждений: роль `gis_human`, журнал решений, очередь |
| `sql/008_concepts.sql` | справочник понятий `kb.concept`, ссылка на него из связей |
| `sql/009_concept_queue.sql` | понятия встают в очередь к человеку (номер для панели, вид в журнале) |
| `sql/010_model_digest.sql` | отпечаток весов модели в журнале обращений — чем именно сделан паспорт |
| `sql/011_integrity.sql` | вердикт только членам `gis_confirmer`; версия признака по хешу входа; индексы; закрытые списки |
| `sql/012_kb_citations.sql` | `kb.publication` и `kb.citation` — литература из базы знаний статей, черновиком |
| `sql/013_concept_anchor.sql` | якоря понятий в графе фактов базы знаний, цитата у связи признак-понятие |
| `sql/014_migrations.sql` | учёт применённых миграций (`meta.migration`) |
| `sql/015_feature_check.sql` | машинные проверки признака: важность, переносимость (`meta.feature_check`) |
| `sql/016_feature_term.sql` | снимок словаря признаков (`meta.feature_term`): база не требует репозиторий прогноза |
| `sql/017_api.sql` | схема `api`: устойчивый вид наружу, только подтверждённое, с правами распространения |
| `sql/018_concept_level.sql` | уровни предметной модели: этап процесса → фактор → критерий, дерево и пробелы |
| `sql/019_verdict_removal.sql` | снятие вердикта — тоже вердикт: агент не возвращает подтверждённое в черновик |
| `sql/020_grid_label.sql` | имя сетки у признаков dataset_v6: данные основного листа были подписаны именем соседнего |

Накатывать по одному файлу больше не нужно — есть учёт:

```
python db/migrate.py --состояние    что применено, что ждёт
python db/migrate.py                накатить ожидающие по порядку
```

Каждый файл применяется в своей транзакции и записывается в `meta.migration`
вместе с отпечатком sha256. Правка уже применённого файла останавливает накат:
расхождение отпечатков значит, что база и код разошлись, и это надо разбирать, а
не накатывать поверх. Повторный запуск не делает ничего.

На пустой базе порядок тот же: схема `meta` под учёт создаётся до первой
миграции, дальше накатываются все файлы подряд. Это проверяется на каждый
коммит — см. «Непрерывная проверка».

## Мост к базе знаний статей

Обоснование паспорта признака кончалось словами «публикация не привязана, база
знаний в разработке». База знаний статей — отдельный проект (`georag`, своя
машина с видеокартой): она собирает статьи, режет их на фрагменты и размечает
по понятиям. Словарь понятий у неё — копия `kb.concept`, коды совпадают буква
в букву; это и есть общий узел двух баз:

```
признак → bridge.feature_concept → понятие → база знаний → статья, цитата, страница
```

```
python scripts/db_kb_evidence.py --сухой     # показать, что пришло бы; ничего не пишет
python scripts/db_kb_evidence.py             # записать
```

По каждому черновику паспорта скрипт берёт его понятия и спрашивает базу знаний:
что в статьях написано про это понятие по нашей территории и тем же методом,
которым посчитан признак (`ast` — ASTER, `lin` — линеаментный анализ; таблица
`МЕТОД_ПО_ГРУППЕ` в начале скрипта). Не нашлось — отбор ослабляется до
территории, до метода, до понятия; какой сработал — написано в блоке.

Что ложится в базу — всё черновиком:

| Куда | Что |
|---|---|
| `kb.publication` | статья: DOI, название, год, авторы |
| `kb.citation` | цитата под понятие: дословно, страница, похожесть, решение модели базы знаний |
| `meta.feature_passport.kb_reference` | блок «Литература из базы знаний статей» в конце обоснования |
| `meta.derivation` | ребро «публикация → паспорт» |

Блок виден в панели подтверждений, в карточке паспорта, в поле «Обоснование»:
человек подтверждает смысл признака и литературу под ним одним решением.
Подтверждённые паспорта скрипт не трогает; повторный запуск заменяет блок, а не
дописывает второй. `kb.citation` охраняется тем же триггером, что паспорта:
статус «подтверждён» у цитаты ставит только человек.

Где база знаний — `GIS_KB_URL`, по умолчанию `http://localhost:8000`. На её
машине должен работать сервер (`python georag.py serve`). Если она на другой
машине — поднимается SSH-туннель, и адрес остаётся тем же:

```
ssh -N -L 8000:127.0.0.1:8000 пользователь@адрес-машины-базы-знаний
```

## Исполнитель-модель

Все обращения к языковой модели идут через один модуль `gisdb/agent_llm.py` —
чтобы сменить исполнителя, правится настройка, а не скрипты агентов.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `GIS_LLM_LOCAL_URL` | — | адрес локального сервера; пусто — перебор известных |
| `GIS_LLM_LOCAL_MODEL` | — | имя модели; пусто — спросить у сервера |
| `GIS_LLM_REASONING` | `none` | «размышление вслух» локальной модели |
| `GIS_LLM_CONTEXT_TOKENS` | `16000` | предел задачи: что не влезает сюда, на этой модели не заработает |

Исполнитель один — **локальный сервер моделей** (Ollama, llama.cpp,
LM Studio). Внешние исполнители из модуля убраны: данные проекта наружу не
уходят, ключи не нужны, и длинный прогон не упирается в чужой предел
обращений — именно так оборвались на середине очереди прогоны 17 и 18.

Сервер поднимается вручную и автозапуска не имеет:

```
set OLLAMA_MODELS=%GIS_DB_ROOT%\models
set OLLAMA_CONTEXT_LENGTH=8192
set OLLAMA_KEEP_ALIVE=2h
ollama serve
```

Первый запрос после загрузки модели в память идёт около полутора минут — это
прогрев, а не работа. Ollama выгружает модель через пять минут без запросов,
поэтому `OLLAMA_KEEP_ALIVE=2h` перед длинным прогоном обязателен, иначе
прогрев платится заново после каждой паузы.

Каждое обращение — строка в `runs.llm_call`: модель, время ответа, токены,
число попыток до разбираемого ответа, сам ответ. Это и есть основание для
перехода на локальную модель: один и тот же набор признаков прогоняется
двумя исполнителями и сравнивается по журналу, а не по впечатлению.

## Панель подтверждений

Вторая половина правила «черновик пишет агент, подтверждает человек». Запуск:

```
python -m gisdb.panel          # http://127.0.0.1:8765
```

Панель показывает очередь черновиков — паспорта признаков, паспорта слоёв,
лицензии, понятия, связи признаков с понятиями — и по каждому даёт карточку: черновик
рядом с фактами, на которых он построен. Для признака это ровно тот текст,
который получала модель (`gisdb/feature_facts.py`), — человек судит по тем же
основаниям, а не по красоте формулировки.

| Действие | Что происходит |
|---|---|
| Подтвердить | статус «подтверждён», подпись и время проставляются триггером |
| Отклонить | статус «отклонён»; без указанной причины база решение не примет |
| Сохранить правку | текст исправлен, объект остаётся в очереди |
| Пакетное решение | из списка очереди, для очевидных случаев |

Паспорта признаков сведены в очереди по коду: один код приходит из нескольких
сборок, смысл у него общий, и решение распространяется на все его черновики —
149 прочтений вместо 240.

Понятия (`kb.concept`) стоят в очереди раньше связей по смыслу: определение
решает, какие связи признаков вообще имеют право быть, а род понятия отделяет
рудоконтролирующий фактор от условия наблюдения. Обнажённость и растительный
покров объясняют, что вообще видно на съёмке, и рудным признаком не являются —
на них приходится больше половины связей, заведённых агентом.

### Уровни предметной модели

Понятия лежат не списком, а деревом: **этап процесса → рудоконтролирующий
фактор (или условие наблюдения) → критерий → признак**. Порядок уровней держит
база (`kb.guard_concept_level`, миграция 018): критерий без фактора не
заведётся, фактор под фактором — тоже, и ошибку видно в день ошибки, а не через
месяц на показе.

Уровень «критерий» нужен затем, что без него объяснение участка карты не
складывается. На восьми факторах висят 218 связей, из них 110 на одном
«обнажённость и растительный покров» — ответ «эта клетка перспективна из-за
обнажённости» не объясняет ничего. Критерий отвечает за одну проверяемую вещь:
не «гидротермальные изменения» вообще, а серицит-мусковитовая кайма или вынос
магнетита в зоне переработки.

| Вид | Что читать |
|---|---|
| `kb.concept_tree` | дерево модели: от признака вверх до этапа процесса |
| `kb.concept_gap` | где модель не достроена: фактор без критериев, критерий без признаков, признак без критерия |

Сами критерии заводит `scripts/db_load_criteria.py` — из словаря признаков,
генетической схемы и материалов по Билляхской зоне, черновиками. Языковую модель
он не спрашивает: критерий — основание всех будущих объяснений карты, и домысел
слабой модели ушёл бы в подтверждённое знание базы. Связи «признак — критерий»
не придумываются заново: берутся уже подтверждённые связи «признак — фактор», и
если код признака входит в критерий под тем же фактором, заводится черновик с той
же ролью. Признак, которому критерия не нашлось, остаётся виден в
`kb.concept_gap` — пробел, который видно запросом, честнее полного дерева,
половина которого выдумана.

Три этапа заведены из генетической схемы наследования и перераспределения
золота (ВНИГНИ, версия 2 от 21.10.2026) — черновиками, как и всё, что
подтверждает человек. Этап самому фактору миграция не ставит: это утверждение о
предметной модели, и выносит его человек в панели, иначе подпись под понятием
осталась бы прежней, а содержание изменилось.

Каждое решение ложится в `meta.review`: кто, когда, что решил, почему отклонил,
что именно исправил (поле «было → стало») и сколько времени читал карточку.
Отсюда же представление `meta.model_score` — доля черновиков модели, принятых
человеком: по ней облачная модель сравнивается с локальной не по впечатлению.

### Вход и учётные записи

Учётная запись проверяющего — это **роль базы с паролем**, а не имя в поле.
Панель проверяет пароль единственным способом, который ничего не изобретает:
пробует открыть соединение этой ролью. Дальше все запросы человека идут от его
имени, и отсюда три следствия:

* подпись под решением (`confirmed_by`, `meta.review.reviewer`) берётся из
  учётной записи — подписаться чужим именем нельзя;
* право вынести вердикт даёт членство в `gis_confirmer`, и проверяет его триггер
  базы, а не страница. Читателю кнопки решения не показываются, а если запрос
  послать мимо страницы — отказывает база, и панель объясняет отказ словами;
* своего хранилища паролей у панели нет: утечь из неё нечему. Пароль живёт в
  памяти процесса, пока жив сеанс (12 часов), печенье хранит только случайный
  ключ.

```
python db/add_reviewer.py --кто ivanov --подпись "Иванов И. И."
python db/add_reviewer.py --кто petrov --только-чтение
python db/add_reviewer.py --список
```

Пароль новой записи печатается один раз и в хранилище секретов **не** кладётся:
пароль человека знает только он сам, иначе подпись опять ничья. Этим записи
людей отличаются от служебных ролей (`gis_agent`, `gis_read`, `gis_human`), чьи
пароли лежат в `secrets`, потому что ими пользуются скрипты. Пароль служебной
роли задаётся по-прежнему: `python db/set_password.py gis_human`.

Войти под `gis_human` можно и без заведения личных записей — так работает
одиночная машина. Но тогда в журнале у всех решений одна подпись, и вопрос «кто
именно подтвердил» остаётся без ответа.

Панель по-прежнему слушает только петлевой адрес. Теперь это не единственная
защита, а вторая: открытый порт без пароля больше не отдаёт право подписи. Для
сетевого доступа этого всё равно мало — нужен TLS, иначе пароль учётной записи
идёт по сети открытым.

## Правила, зашитые в базу

1. `gis_agent` не может выполнить `DELETE` нигде, кроме `staging`.
2. Статусы `подтверждён` и `отклонён` в `meta.license`, `meta.layer_passport`,
   `meta.feature_passport`, `bridge.feature_concept`, `kb.concept` ставит только
   член роли `gis_confirmer` (сейчас это `gis_human`) или суперпользователь —
   триггер `meta.guard_confirmation`. Это список разрешённых, а не запрещённых:
   новая роль права на вердикт не получает, пока его не выдали явно
   (`GRANT gis_confirmer TO …`). При подтверждении `confirmed_by` и
   `confirmed_at` заполняются сами.
3. Слой нельзя пометить выселенным (`evicted`) без пометки `evict_note`, как
   его восстановить из источника — триггер `data.guard_eviction`.
4. Отклонение без причины в `meta.review` не записывается — ограничение
   `отклонение_с_причиной`: оно ничему не учит ни агента, ни следующего
   проверяющего.

## Вид наружу и выгрузка

Схема `api` — то, что база показывает наружу: восемь представлений с
устойчивыми именами. Внутренние таблицы меняются каждую неделю, и если
читающий снаружи пишет запросы к `meta.feature_passport` напрямую, то любое
наше изменение ломает его код — а мы перестаём менять схему из страха.

| Представление | Что отдаёт |
|---|---|
| `api.feature` | паспорта признаков: смысл, покрытие, переносимость, важность |
| `api.layer` | слои-источники: поставщик, метод, лицензия, права передачи |
| `api.concept` | понятия предметной модели и место каждого в дереве |
| `api.feature_concept` | связи «признак — понятие» |
| `api.citation` | цитаты из статей под понятиями |
| `api.territory` | территории и сетки |
| `api.redistribution` | по каждому признаку: можно ли отдавать значения и что запрещает |
| `api.summary` | состав базы одним запросом |

Два правила этой схемы, оба неслучайные:

1. **Только подтверждённое человеком.** Черновик — незаконченная работа
   агента; уйдя в выгрузку, он будет прочитан как знание базы. Исключения —
   машинные проверки и словарь: они подтверждения не требуют по смыслу.
2. **Распространяемость видна сразу.** 34 слоя из 40 передавать нельзя, и это
   касается не только слоёв, но и значений признаков, из них посчитанных.

```
python scripts/db_export.py --проверить     что попадёт в выгрузку
python scripts/db_export.py                 метаданные
python scripts/db_export.py --значения      плюс значения, разрешённые к передаче
```

Выгрузка кладёт CSV (разделитель «;», UTF-8 с меткой — чтобы Excel с русскими
настройками открыл их правильно) и `ПРОЧТИ.txt`, где перечислены лицензии всех
источников, сказано, что исключено и почему. Каждый файл записывается в журнал
прогонов артефактом с отпечатком: видно, что именно и когда ушло наружу.

Значения признаков по умолчанию не выгружаются вовсе: их 11,7 млн, и они несут
в себе содержимое слоёв-источников. С ключом `--значения` выгружаются только
те, у которых **все** слои-источники разрешено распространять — на 23.10.2026
это 85 признаков из 149 и 6 853 897 значений, примерно 245 МБ. Признаки,
посчитанные внутри проекта без слоя-источника, в выгрузку значений не попадают:
решение по ним принимает человек, а не умолчание скрипта.

## Образец для показа

Показать базу можно двумя способами: рассказать о ней — или дать потрогать.
Второе убедительнее, но полную базу отдавать нельзя. Выгрузка в CSV эту задачу
не решает: она отдаёт таблицы, а показать надо работающую систему — панель
подтверждений, происхождение, правила, которые не дают агенту подтвердить свой
же черновик.

```
python scripts/db_demo.py --проверить     что останется и что уйдёт
python scripts/db_demo.py
```

Собирается так: последний дамп рабочей базы разворачивается в отдельную базу
`gis_au_u_demo`, туда накатываются миграции, из неё удаляется запрещённое к
распространению, затем снимается дамп образца с описанием и файлом ролей.
Рабочая база не затрагивается; имя базы образца проверяется перед каждым
удалением — скрипт не может снести рабочую.

Состав на 23.10.2026 (`хранилище:/образец`, 68 МБ):

| | в образце | в рабочей |
|---|---|---|
| слоёв-источников | 6, все открытые | 40 |
| признаков | 142 | 240 |
| из них со значениями к передаче | 85 кодов | 85 из 149 |
| значений | 6 853 897 | 11 757 876 |
| понятий, связей | 8, 125 | 8, 218 |

Удалено: 34 закрытых слоя (32 — материалы организации, Copernicus DEM,
разметка проекта), 98 признаков, посчитанных из них, и всё, что на них
ссылалось — паспорта, проверки, связи, решения человека, рёбра происхождения,
строки словаря и 4,9 млн значений. Лицензии, под которыми не осталось слоёв,
тоже удаляются: в образце не должно быть упоминаний того, чего в нём нет.

**Паролей наших ролей в наборе нет.** Файл `роли.sql` создаёт роли без паролей
— их задаёт у себя тот, кто разворачивает. Это отличает набор от комплекта
переезда (`db/backup.py`), где `roles_*.sql` несёт хеши паролей и наружу
уходить не должен. Проверка следит, чтобы в файл ролей образца не попало слово
`PASSWORD`.

Две вещи выяснились только тем, что инструкцию из набора прошли буква в букву:
восстановление «только данных» поверх накатанной схемы падает — миграции 005 и
008 сами засевают строки (пробелы и понятия), — а распараллеленное
восстановление грузит значения раньше ячеек. Поэтому образец отдаётся полным
дампом, а своя система координат накатывается после восстановления.

Образец отказывается собираться из устаревшей копии: первая сборка вышла с
нулём строк словаря признаков — копия была снята за два часа до его загрузки, и
снаружи это выглядело бы не как старая копия, а как база, не знающая своих
собственных признаков.

## Связь с репозиторием прогноза

Признаки считаются в проекте прогноза (`GIS`), и оттуда же взяты эталонные
предметные формулировки. Но **ядро базы проекта не требует**: панель, сбор
фактов и паспортизатор работают, когда рядом нет ничего, кроме базы. Граница:

| Что | Где читает |
|---|---|
| ядро: `gisdb/`, панель, паспортизатор | только базу |
| загрузчики: `db_load_dictionary.py`, `db_fill_checks.py`, `db_register_layers.py` | проект, через `GIS_PROJECT_ROOT` |

Так знание остаётся в одном месте — словарь признаков по-прежнему единственный,
в проекте, — а база перестаёт быть приложением к исследовательскому
репозиторию. Загрузчики переносят в базу то, что посчитано в проекте, вместе со
ссылкой на файл и его отпечатком.

```
python scripts/db_load_dictionary.py --проверить    отстал ли снимок словаря
python scripts/db_load_dictionary.py                обновить снимок
```

Снимок кладётся в `meta.feature_term`: группа, техническое описание («что это
за столбец») и эталонная формулировка эксперта. Подтверждения человеком он не
требует — это перенос уже написанного, а не суждение. Чего словарь не покрывает,
видно в `meta.feature_term_gap`; на 23.10.2026 пробелов нет — все 149 кодов
описаны, и у всех есть формулировка эксперта.

Что проверяется само: `tests/test_независимость.py` разбирает код `gisdb/` и
валит сборку, если там снова появился `import src`. Вернуть зависимость одной
строкой легко, и заметно это стало бы только у покупателя.

## Копии и проверка восстановления

```
python db/backup.py            копия: дамп, роли, описание восстановления
python db/restore_check.py     развернуть последнюю копию и сверить с рабочей
```

`backup.py` кладёт в `<хранилище>\backup` три файла — сжатый дамп, роли с
паролями и описание порядка восстановления с версиями сервера, — и записывает
копию в журнал прогонов тремя артефактами с отпечатками sha256.

`restore_check.py` проходит обратный путь целиком: поднимает отдельную базу
`gis_au_u_restore_check`, восстанавливает в неё дамп, накатывает свою систему
координат, сверяет количества строк по 17 таблицам с рабочей базой, проверяет
наличие SRID 990018 и четырёх ролей в файле ролей — и удаляет проверочную базу
за собой. Рабочей базы он не касается; имя проверочной проверяется отдельно,
чтобы скрипт физически не мог снести рабочую.

Копия, снятая с живой базы, отстаёт от неё на строки журналов, добавленные
после снимка. Это не потеря, и скрипт её отличает: все строки копии обязаны
найтись в рабочей базе, а лишние — иметь номера больше последнего номера в
копии. В выводе это «копия старше на N», а не «НЕТ».

Отпечаток дампа пишется и в артефакт прогона, сделавшего копию, и во вход
прогона, её проверившего, — два отпечатка сходятся, и видно не «копию
проверяли», а «проверяли вот эту копию».

Расписание (заводится один раз, от текущего пользователя, права
администратора не нужны):

```
schtasks /create /tn GIS-DB-backup /sc weekly /d SUN /st 21:00 ^
  /tr "\"C:\Users\Grisha\GIS\.venv\Scripts\python.exe\" \"C:\Users\Grisha\GIS-agent-db\db\backup.py\""

schtasks /create /tn GIS-DB-restore-check /sc monthly /d 1 /st 22:00 ^
  /tr "\"C:\Users\Grisha\GIS\.venv\Scripts\python.exe\" \"C:\Users\Grisha\GIS-agent-db\db\restore_check.py\""
```

Проверка идёт через час после копии и берёт последний дамп — то есть
свежесделанный. Снять задачи: `schtasks /delete /tn GIS-DB-backup /f`.

## Непрерывная проверка

`.github/workflows/checks.yml`, на каждый коммит в `main` и на каждое
предложение изменений. Две работы:

| Работа | Что проверяет |
|---|---|
| без базы | что репозиторий собирается и проверки проходят на машине без базы |
| установка с нуля | пустой Postgres → роли → все миграции по порядку → все проверки |

Вторая важнее первой. Проверки и так запускаются на рабочей машине, а вот
«ставится ли база с нуля» там не проверить ничем: живая база накапливалась
месяц, роли завели руками, миграции 001-014 зарегистрировали задним числом.
Первый же прогон этой работы нашёл то, чего на живой базе не видно: учёт
миграций создавался в схеме `meta`, которой на пустой базе ещё нет, и установка
падала на первом шаге.

Проверки, которым нужна живая база, пропускаются, когда её нет. Недоступность
выясняется один раз на прогон (`tests/conftest.py`): раньше каждая такая
проверка пробовала подключиться сама, и на машине без базы прогон упирался в
отказы по 10 секунд — четыре с половиной минуты вместо тридцати секунд.

```
pytest tests -q                         всё, что доступно
pip install -r requirements-dev.txt     зависимости проверок
pip install -r requirements-geo.txt     геометрия: только регистрация слоёв
```

## Перенос на другой сервер

Структура базы целиком лежит в миграциях `sql/001`–`012`, а данные
воспроизводятся скриптами из `data/processed`. Поэтому переехать можно двумя
путями, и оба рабочие.

**Путь А — пересобрать (медленнее, надёжнее).** На сервере: PostgreSQL с
PostGIS → миграции 001–007 → `scripts/db_load_datasets.py` →
`scripts/db_fill_passports.py`. Около получаса, ничего не тащим по сети,
кроме репозитория. Годится, пока данные воспроизводимы из файлов.

**Путь Б — перевезти (быстрее).** `python db/backup.py` делает дамп базы,
дамп ролей и записку с порядком восстановления; порядок описан в самой
записке. Дамп сжатый: 997 МБ базы дают 113 МБ файла.

Чего не хватит в любом случае:

| Что | Почему |
|---|---|
| Система координат SRID 990018 | содержимое `spatial_ref_sys` принадлежит расширению PostGIS и в дамп не попадает — накатить `sql/004_srid.sql` вручную |
| Роли и пароли | не входят в дамп базы, отсюда отдельный `roles_*.sql` |
| Файлы вне базы | `raster`, `incoming` копируются отдельно; в базе лежат только ссылки |
| Версия сервера | дамп из 18-й в 16-ю не зальётся, сервер должен быть не старше |

Настройка на новом месте — только переменные окружения, код не правится:
`GIS_DB_HOST`, `GIS_DB_PORT`, `GIS_DB_NAME`, `GIS_DB_ROOT`,
`GIS_DB_PASSWORD_<РОЛЬ>`.

Пути файлов пишутся в базу в переносимом виде — `проект:/data/processed/…`
и `хранилище:/raster/…` (`gisdb/db.py`, функции `store_ref` и `store_path`).
Буквы диска в базе нет нигде.

Что добавится именно на сервере: доступ по сети вместо `localhost`
(`pg_hba.conf`, TLS, порт 5432), автозапуск службой, регулярный `db/backup.py`
по расписанию.

### Исполнитель-модель на сервере

Исполнителем на сервере остаётся локальная модель — внешних в проекте нет.
Решает железо: модель на 12 млрд весов без видеокарты считает единицы токенов
в секунду, и 240 паспортов будут делаться часами. Поэтому первый вопрос при
переносе — есть ли на сервере видеокарта и сколько на ней памяти
(`nvidia-smi`). Нет видеокарты — паспортизацию придётся оставить на рабочей
машине, а на сервере держать только базу.

Порядок для сервера с видеокартой от 12 ГБ:

1. поставить Ollama (на Linux — установочный скрипт с сайта проекта), она
   поднимется службой и сама переживёт перезагрузку;
2. указать ей каталог моделей на большом диске: `OLLAMA_MODELS=/путь/models`
   в настройках службы — веса весят 7-8 ГБ и системный раздел ими забивается;
3. `ollama pull gemma4:12b` — если у сервера есть выход наружу. Если нет,
   каталог моделей переносится копированием с рабочей машины: там лежат
   обычные файлы, докачивать ничего не надо;
4. длина окна при запуске службы — `OLLAMA_CONTEXT_LENGTH=8192`, и
   `OLLAMA_KEEP_ALIVE=2h`, чтобы модель не выгружалась между заданиями;
5. на стороне проекта — `GIS_LLM_REASONING=none` (без этого каждый паспорт
   стоит вшестеро дороже) и, если сервер моделей стоит не на той же машине,
   `GIS_LLM_LOCAL_URL`.

Движок при этом сменный: `agent_llm.py` разговаривает с любым сервером,
понимающим общий интерфейс, и сам перебирает известные порты. Если на сервере
удобнее llama.cpp — меняется одна переменная окружения, код не правится. Выбор
в пользу Ollama сделан ради переноса: она ставится одной командой, сама
определяет ускоритель и сама регистрируется службой, тогда как llama.cpp
требует подобрать сборку под драйвер и написать файл службы руками.

Отдельный вопрос при переносе — **лицензия весов**, а не движка: сами движки
свободны, а модели нет. Семейство `gemma` идёт под собственными условиями
Google, `qwen` — под Apache 2.0. Если у организации к этому есть требования,
менять надо модель, а не движок: `qwen3.5:9b` (6.6 ГБ) для нашей задачи
сопоставим.
